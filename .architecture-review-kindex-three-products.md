# Kindex Three-Product Architecture

## §0 Stakes

**Classification: expensive-to-revert.** The product contracts, authority model,
Git artifact format, identity bindings, and host integration require coordinated
migration to reverse. A boundary failure that discloses Personal material into a
Company store or distributed Git clone is an **irreversible failure mode**: code
rollback cannot recall already-replicated data.

The design therefore treats privacy eligibility and publication authority as
structural admission gates. Statistical classification and retrieval ranking may
lose recall, but cannot widen disclosure.

## §1 Problem statement

Brownfield coding requires durable knowledge at two distinct shared scopes:
organization-wide knowledge that applies across systems, and repository-specific
knowledge that travels with one codebase. Personal conversations and memory must
remain a third, private product and must never be mounted merely because the same
person starts coding. Current Kindex has profiles, project `.kin/` artifacts,
weighted nodes and edges, hybrid retrieval, and agent hooks, but it does not yet
provide an engine-enforced Company + Codebase federation, authenticated immutable
repo facts, safe conversational knowledge extraction, working-set-aware retrieval,
or uniform Codex/Claude behavior. The result must improve brownfield decisions by
putting decisive constraints, rationale, failure modes, and unresolved questions in
the agent's working set at the dependent edit without turning a routing mistake into
an unrecoverable privacy incident.

## §2 Proposed approach

### 2.1 One kernel, three authority products

Kindex Core owns a common event model, admission pipeline, query/projector protocol,
signing and validation, local caching, and host adapter contract. It is exposed as:

1. **Kindex Personal** — owner-private conversations and memory. It is never mounted
   in coding mode.
2. **Guildhall (Kindex Company)** — organization knowledge: architectural principles,
   standards, ownership, operating constraints, system relationships, incident
   lessons, and history. It informs all authorized company coding work.
3. **Kindex Codebase** — signed, Git-carried `.kin/` knowledge whose durable utility
   is specific to one repository. It informs only that repository.

An ephemeral `SessionInput` and an out-of-worktree candidate/outbox store are
pipeline infrastructure, not additional products or authorities.

### 2.2 Engine-owned source resolution

For a coding session, Kindex Core resolves exactly `authenticated Guildhall +
authenticated current Codebase + ephemeral SessionInput`. It derives the company,
principal, canonical repository identity, revision, and trust roots, then returns a
mount receipt listing the admitted authorities and versions. Codex, Claude, a hook,
an environment variable, and clone-controlled `.kin/config` may request a narrower
view but cannot add Personal, substitute a company, or widen access. A repo without a
valid trust root is mounted as quarantined evidence, not trusted knowledge.

Repository identity is a stable random identifier in an owner-issued certificate
signed by the relevant Company or public-project trust root; it is never derived
solely from a path, remote URL, forge, or clone-controlled configuration. Every
Codebase event binds that repository ID and its issuing authority. A fork receives a
new repository ID. Facts imported from upstream retain the upstream ID and authority
and become local authority only through an explicit signed import/adoption event.
Forge migration requires a signed identity-alias event; subtree and history imports
confer no authority merely because their bytes appear in the Git DAG.

Sources remain physically and logically separate. Federation preserves source
authority on every result; it does not import all facts into one database. Company
facts are referenced from `.kin/` by stable fact ID, content digest, and validity
interval rather than copied into repositories.

### 2.3 Knowledge atoms, not message routing

Messages are evidence containers, not classification units. One message may contain
private biographical context, a global architectural principle, a repository-specific
constraint, and conversational filler. The capture pipeline proposes minimal
**knowledge atoms**, each with:

- kind: principle, invariant, decision, rationale, failure mode, operational
  constraint, compatibility contract, idea, question/Unknown, exception, or evidence;
- semantic logical key and scope: company/domain/service/repo/path/symbol/edit seam;
- decision triggers and candidate actions constrained;
- conditional `loss_if_absent` (distortion consequence), not generic importance;
- evidence references, authority, asserted and valid time, referent digest, and
  confidence;
- causal/supersession parents and relations such as `applies`, `specializes`,
  `implements`, `depends_on`, `exception_to`, `contradicts`, `redundant_with`, and
  `complements`;
- proposed destinations: Personal, Company, one or more Codebases, or none.

Multi-label classification has proposal authority only. It may create zero-authority
candidates and destination-specific rendered previews; it cannot publish, sign,
change visibility, or infer a destination from content alone. The session's explicit
mode and authorized repositories bound which destinations may even be proposed.

### 2.4 Destination-minimized promotion

Promotion has two lanes:

1. **Evidence-derived lane.** A typed atom may auto-materialize only when every
   textual field is deterministically rendered from allowlisted shareable evidence:
   repo-relative content-bound code spans or symbols, tests, commits, issues, PRs,
   ADRs, or an eligible Guildhall fact reference. Session prose, people/client facts,
   secrets, and testimony cannot enter this lane.
2. **Testimonial lane.** Rationale, style, concepts, ideas, hypotheses, and any
   de-identified derivative of conversation require a named authorized human to
   approve the exact destination-specific bytes. The signed assertion says that a
   human approved that projection; it does not claim the source conversation was
   exported.

Testimonial promotion v1 presents exactly one atom for exactly one destination per
approval request. Kindex Core rejects multi-atom and multi-destination approvals even
if a client constructs one; the UI also exposes no `accept all` operation. Core shows
at most three testimonial requests to one principal in one repository session and
defers the remainder without repeated prompting. Batch approval remains disabled
until a controlled comparison against single-atom review observes zero critical
unsafe approvals in at least 300 seeded critical trials (a one-sided 95% upper bound
below approximately 1%) and no more than a one-percentage-point degradation for
noncritical unsafe approvals. In operation, ten consecutive approvals completed in
under two seconds each, or a trailing-20 acceptance rate above 95% with median dwell
below three seconds, disables further testimonial promotion for that session and
requires later review. These are conservative v1 tripwires to be revised only through
measured policy versioning, never silently tuned by the classifier.

De-identification is a transformation, not an authority grant. A shared projection
must omit names and indirect identifiers, contain no raw transcript/excerpt/pointer or
transcript digest, pass scanners and re-identification checks as defense in depth, and
satisfy the normal exact-byte approval. The private lineage vault is the actual
privacy boundary for the reversible Personal-to-projection mapping. It is local-only,
encrypted at rest under a user-owned key obtained from the OS credential store, denied
to Company/Guildhall administration and synchronization, and excluded from default
backups and telemetry. The source mapping exists only until every destination is in a
terminal state or seven days have elapsed, whichever comes first; then cryptographic
deletion removes it. A durable local receipt may retain destination event IDs and
status but no Personal source identifier, excerpt, pointer, or digest. Managed-device
access and legal process can still expose the vault while it exists; documentation
must state that limit before enterprise deployment.

A single candidate may produce different minimized atoms for Company and multiple
Codebases. Kindex does not pretend this is a distributed transaction. A durable
promotion intent drives independent idempotent writes, each with its own event ID,
authorization decision, signature, and receipt. Partial success is explicit and
retryable. A private correlation receipt relates the projections without placing a
cross-store linkage or Personal source identifier in shared artifacts.

### 2.5 Immutable outside data and owned correction

Guildhall exposes a signed append-only claim/event API and verified local read cache.
Codebase knowledge is stored as canonical, content-addressed immutable events under a
versioned `.kin/` layout with a deterministic derived manifest. Event kinds include
assertion, supersession, retraction/tombstone, exception, conflict resolution,
Unknown, and Unknown closure. Ordinary correction appends an apology/supersession;
it does not mutate history.

Every event includes schema version, content hash, authority, logical key, scope,
typed payload, evidence, signer key fingerprint and signature, asserted time, valid
interval, referent binding, parents, and conditional distortion loss. Display identity
is resolved outside Git and may be erased; Git retains only a pseudonymous audit key.
Raw personal identifiers are forbidden because distributed clones cannot guarantee
erasure.

Git merge is set union of immutable event files. Concurrent assertions for one logical
key become multiple current heads. The materializer never uses timestamp or path
specificity to invent a winner. Company domain stewards own Company predicates;
Codebase maintainers own repository predicates. A Codebase exception to Company
policy is valid only when it cites a Company-authorized exception event. Otherwise
the contradiction blocks dependent trusted projection.

### 2.6 Architectural knowledge across scopes

Guildhall stores global architectural ideas as first-class `architecture_principle`
or `architecture_constraint` atoms with owner, applicability, counterexamples,
validity, and evidence. A repository `.kin/` event references the exact Company fact
ID + digest + validity and states its local relationship:

- `applies`: used unchanged here;
- `specializes`: narrowed for this repository;
- `implements`: concrete code/test evidence realizes it;
- `exception_to`: explicitly authorized departure;
- `contradicts`: unresolved evidence that the global idea does not fit.

Thus the repo records the architectural consequence germane to the codebase without
copying global prose. Superseding the Company fact makes dependent repo assertions
stale and emits scoped Unknowns for revalidation rather than silently replacing their
meaning.

### 2.7 Admission and projection

Every source passes deterministic admission before ranking: supported schema,
content-address match, signature, signer authorization at assertion time, current
access scope, validity, referent freshness, revocation, and destination policy.
Unsigned or clone-injected `.kin` content remains visible only in a quarantine view.
Stale or conflicting facts may be shown as historical evidence but cannot enter the
trusted working set; Kindex emits an Unknown naming the dependent decision and
evidence required for closure.

The query contract accepts task/decision context, repository identity and revision,
the current working-set fact IDs/digests, and hard resource ceilings. Candidate
retrieval remains hybrid. Final selection is set-conditional: a greedy submodular
coverage objective estimates the marginal expected decision utility of each eligible
atom given the current set, discounts explicit/semantic redundancy, and charges
retrieval plus context cost. Explicit dependency bundles cover known complementarities
that a pure diminishing-returns model cannot represent. Retrieval escalates through
raw evidence tiers and stops when estimated marginal VOI is not greater than the next
tier's cost. VOI is initially an **instrumented, uncalibrated surrogate** using distortion loss,
decision-trigger probability, authority/freshness, candidate-action reduction, and
observed outcomes; calibration is an aspiration with an explicit experiment, not a
property asserted at launch. On noncritical benchmark and opt-in development tasks,
the evaluator sometimes adds one eligible under-ranked atom without removing any
high-loss atom, logs its selection propensity, and measures outcome delta. Periodic
held-out counterfactual and propensity-aware evaluation estimates value the live
selector would otherwise never observe. Exploration can never alter admission,
withhold mandatory evidence, or run on Critical work.

Unknowns are first-class atoms with scope, owner, dependent decision, validity,
evidence required for closure, and status. A resident high-distortion Unknown causes
the agent to inspect the named evidence or ask a specific question before the
dependent edit. Generic conversational questioning is not rewarded.

### 2.8 Codex and Claude lifecycle parity

Both adapters implement the same Core protocol:

`begin -> observe -> checkpoint -> promote -> end`

`begin` discovers the Git root, verifies mounts, returns a mount receipt, and primes a
minimal projection. `observe` receives bounded host events and proposes atoms into the
external candidate store. `checkpoint` evaluates changed decision seams, captures
Unknowns, asks targeted questions, and presents at most three individually approved,
single-destination testimonial atoms.
`promote` executes destination-specific admission and the durable outbox. `end`
reports unresolved high-loss Unknowns and pending candidates; it does not dump a
transcript.

Hook coverage is a measured capability. If Codex or Claude hooks are missing, disabled,
or awaiting host approval, startup emits one actionable warning and `kin doctor`
reports the exact missing lifecycle events. MCP calls remain the explicit fallback,
but Kindex makes no claim of automatic capture when observation is absent. Matched
fixture transcripts must yield the same atom proposals and mounts on both hosts.

### 2.9 Brownfield Factory boundary

The Factory is outside Company and Codebase trust boundaries. It receives an expiring,
read-only, task-scoped, signed data envelope containing claims, scope, source authority,
validity, evidence references, distortion loss, relations, conflicts, and Unknowns.
It receives no Personal material, raw prompt/transcript, arbitrary command field, or
executable text. Free text is delimited hostile evidence and never interpolated into
shell, policy, or system instructions. Kindex informs; Pact/Tessera and human-ratified
artifacts authorize. Factory outputs return as candidates and cannot directly mutate
Guildhall or `.kin/`. In particular, the Factory may emit only an
`exception_request`, never a promotable Company or Codebase `exception_to` event. A
Company domain steward must independently author a Guildhall exception authorization
through the Company authority path. Only after that event already exists may a
Codebase maintainer promote a repository `exception_to` adoption that cites it. A
generic testimonial approval is never Company exception authority.

The brownfield-optimized unit is not a document summary. It is an atom that changes a
candidate implementation decision: a constraint that rules actions out, an invariant
whose absence has measurable distortion, a rationale that distinguishes plausible
wrong patches, a failure mode, an applicability edge from a global principle, or an
Unknown that prevents false completion. Instrument requested/returned/resident atoms,
dependent edit events, tool calls, outcome, reuse versus duplication, and false-done;
never raw chain-of-thought.

### 2.10 Repository and validation topology

- Existing `kindex` remains the shared Core, Personal product, Codebase event format,
  projector, and host adapters so the legacy migration is tested where it must land.
- New `guildhall` repository contains the Company authority service, identity/role
  adapters, access policy, signed event API, cache protocol, and operations surface.
- A separate disposable `kindex-boundary-lab` repository/fixture models multiple
  clones, principals, branches, companies, malicious `.kin`, key revocation, offline
  caches, conflicts, de-identification, and cross-destination partial failure.

The fixture proves boundary mechanics; it is not evidence of brownfield utility.
Performance is established on public inherited codebases first and then an aggregate-
only MEA arm.

### 2.11 Build and measurement order

Phases 1 and 2 are explicitly research-only information-shape ceilings over a frozen,
known-eligible evidence corpus. Every artifact is admitted by the experiment fixture
before randomization, so authority is invariant across arms. These phases neither
model end-to-end production admission nor calibrate the production selector.

1. **Artifact-class ablation:** baseline, types, tests, history, all, and token-matched
   same-repo distractors; fixed model/harness/tools/budget; held-out tests; measure
   supplied/consumed tokens, constraint presence, edit-time residency, false-done,
   reuse/duplication, and gain per thousand tokens. Falsifier: relevant and distractor
   arms are indistinguishable.
2. **Bits measurement:** accepted-patch NLL and its margin over plausible-wrong patches
   under each context arm. Falsifier: context improves success without corresponding
   likelihood separation.
3. **Projector and authority foundation:** build the minimal authority, repository
   identity, event, and admission boundary before any live projection; then add
   engine-owned mounts, atom proposal benchmark, promotion/outbox, Company/Codebase
   federation, VOI loop, Unknowns, structured inter-agent claims, and edit-time
   residency. Falsifier: it
   fails to outperform relevance top-k per token or cannot hold the zero-disclosure
   boundary on adversarial classification tests.
4. **Demand-derived compiler:** precompute only hot relations demonstrated by projector
   logs. Raw evidence stays version-keyed and derived views disposable.

Current `.kin/index.json` remains readable as legacy untrusted input during a versioned
dual-read migration. New event writers do not reinterpret or overwrite old snapshots.
Mixed-version merge and unknown-field passthrough tests are mandatory before rollout.

## §3 Failure modes

1. **Personal leakage into shared products (irreversible):** physically separate mounts,
   candidate stores, destination-specific admission, no transcript linkage, exact-byte
   approval, and cross-boundary canaries. A classifier cannot publish.
2. **De-identification failure:** indirect identifiers survive or multiple projections
   enable linkage. Treat de-identification as testimonial-only, minimize independently,
   run adversarial re-identification tests, and retain no shared correlation key.
3. **Approval fatigue:** repeated low-value prompts train blind acceptance. Core—not
   UI convention—enforces single-atom/single-destination approval, the three-request
   session ceiling, no `accept all`, and the dwell/acceptance tripwires. Batch support
   cannot ship before the controlled noninferiority and zero-critical-miss gate passes.
4. **Malicious clone/PR poisoning:** an attacker commits fake `.kin` instructions.
   Fail admission on hash/signature/authority/policy; treat even admitted prose as data,
   not commands.
5. **Conflicting merged invariants:** dependent projection returns `blocked_conflict`
   with both heads, owner, affected decisions, and closure evidence. The Factory may
   continue only on independent work proven not to depend on the logical key; it may
   not choose a side.
6. **Company offline/stale:** if a required blocking/safety fact is expired or freshness
   cannot be established, emit a high-loss Unknown and block dependent edits/promotion.
   Advisory facts may be used as explicitly stale evidence under a configured maximum
   age. No generic "offline means proceed" mode.
7. **Partial multi-destination write:** independent receipts expose committed, refused,
   and pending projections; retry uses stable idempotency keys. No rollback claim is
   made for an already-replicated destination.
8. **Concurrent writers:** immutable union may produce multiple heads. Materialization
   surfaces the conflict; clocks never settle it.
9. **Stale upstream principle or code evidence:** dependent atoms leave trusted recall
   and produce Unknowns. History remains inspectable.
10. **Classifier under-capture:** useful rationale stays local or absent. Explicit agent
    capture and human nomination recover recall without weakening publication gates.
11. **Redundant or complementary retrieval error:** similarity suppresses distinct facts
    or misses a necessary pair. Typed redundancy, dependency bundles, working-set logs,
    and ablations expose the error.
12. **Prompt/command injection through facts:** strict data schemas, quoting, field
    non-interpolation, and hostile fixtures protect the Factory and host adapters.
13. **Identity/erasure illusion:** pseudonymous keys may be correlated through Git/PR
    evidence. Documentation forbids anonymity claims and provides key revocation, while
    acknowledging that historical Git data persists.
14. **Hook absence or host divergence:** capability receipts and paired conformance tests
    prevent silent claims of capture parity.
15. **Telemetry leakage or Goodharting:** log structured IDs and observable events, not
    prompts/chain-of-thought; keep held-out success as the governing outcome.

## §4 Constraints

- Personal is never mounted in coding mode and cannot be added by host request.
- Company and Codebase remain distinct authorities when jointly projected.
- Only Kindex Core resolves mounts and performs admission.
- Classification may propose several destinations but authorizes none.
- Testimonial v1 approvals contain exactly one atom and one destination; Core rejects
  batching and exposes no bulk-accept authority.
- Shared destinations receive independently minimized atoms, never a copied message.
- Raw transcript text, excerpt, pointer, digest, and reversible Personal linkage are
  forbidden in tracked `.kin/` and Guildhall testimonial projections.
- Unverified, stale, revoked, unauthorized, or conflicting facts cannot enter trusted
  projection.
- Git/shared corrections append; normal operation is never last-writer-wins rewriting.
- Every shared atom carries authority, scope, provenance, valid time, content binding,
  signer, supersession/parent semantics, and conditional distortion loss.
- Company facts own global architectural principles; repo facts reference and state the
  local relationship rather than duplicating them.
- Company exceptions require Company-authorized exception events.
- Factory output can request an exception but cannot author or promote one; generic
  testimonial approval is never Company exception authority.
- VOI and learned ranking run strictly after deterministic eligibility.
- High-loss unresolved Company facts block only demonstrably dependent work; the
  projector must name that dependency.
- Factory projections are data-only, least-privilege, non-executable, and non-authorizing.
- Secret/PII/de-identification scanners are defense in depth, not authority.
- Promotion is idempotent per destination and makes partial success observable.
- Kindex never automatically commits repository changes.
- Codex and Claude implement and pass the same lifecycle contract.
- Existing profiles, MCP clients, and `.kin` repos receive a versioned dual-read
  migration; an old artifact is never silently promoted to trusted new semantics.

## §5 Assumptions

- **Load-bearing:** Guildhall can authenticate principals, signing keys, domain owners,
  maintainers, delegation, and revocation at the relevant asserted/valid time.
- **Load-bearing:** repository identity and trust roots use owner-signed stable IDs;
  forks, imports, subtree merges, and forge moves cannot acquire authority solely by
  moving clone-controlled bytes.
- **Load-bearing:** single-atom/single-destination approval, the three-request session
  ceiling, and Core-enforced tripwires keep testimonial v1 below the defined fatigue
  boundary; batching remains absent until its falsifiable release gate passes.
- **Load-bearing:** shared products retain no reversible link to Personal source
  material. The temporary encrypted private lineage vault does retain that link and
  its user-owned key, access controls, and bounded destruction are the actual privacy
  boundary while it exists.
- **Load-bearing:** the immutable event format can coexist with legacy `.kin` without
  old merge drivers corrupting or trusting new fields.
- **Load-bearing:** a dependency from a conflicted/expired fact to an edit can be made
  explicit enough to block narrowly rather than halt every Factory run.
- Structured residency, logged selection propensities, bounded eligible exploration,
  and held-out counterfactual evaluation can eventually calibrate a useful VOI
  surrogate without raw prompts.
- Most positive complementarity can be represented through explicit dependency bundles;
  the remaining selector can use a tractable diminishing-returns objective.
- Both hosts expose enough lifecycle events for useful parity, with explicit MCP
  checkpointing as a visible fallback.
- Public brownfield tasks plus aggregate-only MEA results provide credible external
  validity without exposing proprietary code.

## §6 Limitations

- Kindex informs; it does not authorize code, deployment, or production operations.
- It cannot prove free-form prose is codebase-germane or perfectly de-identified.
- It cannot erase data from every Git clone, cache, or already-served projection.
- Initial VOI estimates are uncalibrated surrogates. Without bounded exploration they
  systematically undervalue atoms the live selector underranks; even with exploration
  they are estimates, not exact causal utility.
- Edit-time residency proves availability, not causal use.
- Offline Company operation necessarily trades freshness for availability; some work
  will block when required facts cannot be validated.
- Pseudonymous keys are audit identifiers, not anonymity guarantees.
- It does not replace code, types, tests, runtime traces, ADRs, Pact, Tessera, or human
  ownership.
- It does not build a graph of everything, a repo-wide summarizer, or an AGENTS.md
  generator.
- Compiler work remains deliberately absent until observed projector demand exists.
- The boundary fixture proves mechanics, not improved brownfield outcomes.

## §7 Alternatives considered

1. **One graph with audience labels and heuristic routing:** rejected because a routing
   bug becomes an irreversible disclosure and fact ownership is ambiguous.
2. **Classify whole messages:** rejected because one utterance commonly mixes scopes;
   atoms enable destination minimization and multi-label proposals.
3. **Current hierarchical `.kin` inheritance:** useful for configuration, insufficient
   for authenticated multi-authority facts, independent invalidation, and privacy.
4. **Copy Company knowledge into every repo:** rejected because copies stale
   independently, leak scope, and obscure the owning authority.
5. **Codebase-only or Company-only memory:** each omits one source essential to
   brownfield work.
6. **Three separate engines/protocols:** rejected because enforcement and host behavior
   would drift; one kernel with separate authorities keeps the safety rules common.
7. **Distributed all-or-nothing promotion transaction:** rejected because Company and
   Git are independently available outside data; durable intent, idempotent messages,
   receipts, and apologies describe reality.
8. **Compiler-first summaries or larger prompts:** rejected by the unknown future
   decision variable and the same-repo distractor falsifier.
9. **Additive top-k selection:** rejected because value is conditional on the current
   set and top-k overselects correlated facts.
10. **Build and validate only in a new greenfield repo:** rejected because it cannot
    exercise migration or brownfield utility. Use a new Guildhall service and a new
    adversarial fixture, while changing Core in the existing repo and measuring on
    inherited codebases.

Adjacent prior art found through Centaur—Pact, Cartographer, Stigmergy, Constrain, and
Witness—should be integrated at their existing boundaries rather than duplicated.
None provides this three-authority federation, atom promotion, and VOI projector.

## §8 Open questions

1. Guildhall hosted, self-hosted, or both; and the tenant/data-residency contract.
2. Exact company identity/key enrollment, delegation, rotation, revocation, and
   historical-at-assertion authorization proof.
3. **Resolved for v1:** owner-signed stable repository IDs; new IDs for forks;
   authority-preserving upstream imports; signed forge aliases; no implicit authority
   from subtree/history imports. Remaining implementation detail is the certificate
   envelope and public-project root enrollment UX.
4. The initial conditional distortion taxonomy and whether costs are ordinal,
   domain-specific utility units, or both.
5. Which complementarities require explicit bundles and whether learned conditional
   gain should eventually relax the submodular approximation.
6. Exact blocking/advisory Company fact types, freshness SLOs, and offline maximum ages.
7. Exact `.kin/events/` layout, manifest, signature envelope, and dual-read migration
   schedule from `index.json`.
8. **Resolved for v1:** no batching, one atom and destination per approval, at most
   three prompts per repository session, Core-enforced tripwires, and a 300-critical-
   trial/noninferiority gate before any future batch feature. The later question is
   whether observed data ever justifies enabling a versioned batch policy.
9. The labeled atom corpus, adjudication process, multi-label metrics, de-identification
   attack suite, and the acceptable false-positive proposal rate. Publication leakage
   tolerance remains zero regardless of classifier metrics.
10. Query-log retention, access, and privacy policy.
11. Which global architectural relationships are required in v1 beyond `applies`,
    `specializes`, `implements`, `exception_to`, and `contradicts`.
12. Public benchmark selection, model family, run count, and spend cap.
